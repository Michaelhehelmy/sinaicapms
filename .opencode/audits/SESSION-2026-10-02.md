## 3. Open hazards — read before deploying

### 3.1 `0127` is committed but NOT applied to any database

The migration and the code that depends on it are merged **separately**:

```bash
cd backend && npx wrangler d1 migrations apply campmaster-db --remote   # owner-only
```

Ordering is not cosmetic. Deployed before the migration, the handler's
tenant-scoped meal-id probe matches nothing across tenants (a foreign meal id
still dies on the raw global PK → generic 409) and `meal_lang`'s INSERT binds a
`tenant_id` column that does not exist. That failure mode is **at runtime, not
at boot** — the Worker starts clean and the menu breaks later. Rehearse with
`--local`, or replay the chain in-process via
`backend/tests/meals-tenant-composite-pk.test.js`.

### 3.2 `pos_products` composite PK is BLOCKED, deliberately

`6fd84ff` / `docs/BLOCKED-pos-products-composite-pk.md`. Five of the six
inbound FK edges convert cleanly; the sixth is `storefront_order_items
(product_id) ON DELETE SET NULL`, and SQLite has no per-column `SET NULL`, so
widening the edge either makes every product referenced by a storefront line
**undeletable** (`tenant_id NOT NULL`) or, with a nullable discriminator,
silently **orphans an order line into no tenant** — the critical
cross-tenant-leakage class the safety rules single out. The line carries no
`tenant_id` to key on (it reaches the tenant through `storefront_orders`), and
it is the newest edge in the schema (`0123`), which is why it is easy to miss.
Verdict: **do not author this migration** until `storefront_order_items` grows
a backfilled tenant discriminator.

### 3.3 Round-trip parity is only PARTIALLY closed

Per `docs/audit-2026-09-30-tenant-import-parity.md` §D3 and
`docs/audit-2026-10-02-tenant-import-edge-cases.md` §3.1: `sku`, `email`,
`username` (→ `0126`) and `meals.id` (→ `0127`) are tenant-scoped;
`pos_products.id`, `pos_products.barcode` (manufacturer EAN/UPC — global is
correct) and `meals`/`rooms_new`/`rate_plans_new` `id` handling are not. A
manifest shipping another tenant's explicit `products[].id` still answers the
generic `409 One or more products already exist (duplicate SKU or ID)`.

### 3.4 Explicit `mealCategoryId` is still unvalidated

The `categoryName` pre-flight is name-based. A meal carrying an explicit
`mealCategoryId` is bound **verbatim with no existence check**, so a placeholder
id fails as a raw 500 (`meal_category_id` is `NOT NULL REFERENCES
meal_categories(id)`), not a 400. Out of scope for every mission that has run;
recorded so it is not mistaken for closed.

### 3.5 `scripts/export-tenant.mjs` still carries two false loss claims

The `KNOWN LOSSES` header says *"rooms room_status/cleaning_status: readable
but dropped by re-import"* and the `typeMissing` guard says *"GET
/api/products SELECT omits the column"*. Both statements are false: the import
persists the room statuses (`467b6f9`) and the products SELECT returns `type`
(`d7da499`). The **counters** are worth keeping — they are canaries that
re-fire if a column goes missing again — but the prose misleads. Reported by
A5 in `docs/tenant-import.md` §6; **not fixed**, because the exporter is code
and A5's scope was documentation.

Note the asymmetry A5 pinned down while writing this up: the room statuses
are a **half-closed** round trip. The import leg is fixed; the **exporter
still never emits them** (it only counts them), so a full export → import
cycle still loses them.

## 6. One process hazard from today's parallelism

Four agents shared one working tree and one git index. Two consequences, both
worth the next session's attention:

1. **A `git commit` takes the whole index, not what you added.** A parallel
   `git add` had staged 11 files; the other workstream's subsequent `git
   commit` swept A5's logbook fold into its commit. Content intact (the logbook
   is append-only), attribution wrong. Use `git commit --only <paths>`, and
   check `git diff --cached --name-only` immediately before committing.
2. **A push can "fail" because another agent already pushed your commit.** A5's
   final push was rejected with `is at 1eb21523 but expected dbcb382` — the
   remote was already at A5's own SHA, because the other agent had pushed from
   the same object store. Verify with
   `git merge-base --is-ancestor <sha> origin/main` before treating a rejection
   as a failure.

A rebase in the shared tree would also have needed the other workstream's
unstaged `package.json`/`package-lock.json` edits out of the way; a temporary
`git worktree` was the safe route that left their working tree untouched.
