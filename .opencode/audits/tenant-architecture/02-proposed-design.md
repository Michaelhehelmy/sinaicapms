## LOCKED CONSTRAINTS (constraints, not options — never hedged)

- **D1 — projects table is the isolation boundary; every food/menu/reporting entity scopes by project_id.**
- **D2 — unified storefront.**
- **D3 — one cart/order/payment, line items tagged by project_id.**

No alternative that violates D1/D2/D3 is considered below. Where current code contradicts a constraint (e.g. tenant-grain menu reads in `backend/src/api/meals.js:43-52`, tenant-grain POS product reads in `backend/src/routes/pos/index.js:397-400`, tenant-only reports in `backend/src/api/reports.js:78-84`), current code loses and the constraint wins.

## §1. Target model (two-worlds framing)

**Tenant.** The customer/owner account (e.g. Acacia) — the identity and billing root held in the `tenants` table (`backend/migrations/0001_init.sql:7`; Phase 1 §1.1). A tenant owns N `projects` rows (each carrying that tenant's `tenant_id`), exactly one POS organization (1:1 via `tenant_org_mapping`, `backend/migrations/0041_create_tenant_org_mapping.sql:10-17`), and the shared catalogue layer (one menu catalogue, one product catalogue, one staff roster — Phase 1 §5 bullet 6). Tenants are the scope anchor, never a scoped table (Phase 1 §2.1).

**Project.** A row in the `projects` table (`backend/migrations/0063_rename_camps_to_projects.sql:26-46`; `tenant_id NOT NULL → tenants(id)`, `UNIQUE(tenant_id, slug)`), typed by `project_type` (`camp | supermarket | transportation | restaurant | custom` — `backend/src/api/camps.js:43`). Under D1 the project is the isolation boundary: rooms, bookings, servings, menu/catalogue rows, and revenue each belong to exactly one project (or, for unified-cart headers and tenant-wide promos only, span projects with per-line project tags per D3). Each project closes its own books — the multi-brand operation on one shared ERP with a separate P&L per project (Phase 1 §5 bullet 8). The retained `camp_id` columns on `rooms_new`/`orders`/`meal_schedules`/`rate_plans_new` (all now `REFERENCES projects(id) ON DELETE SET NULL` per `0066:22-24,61-72,101-121` and `0091:20-34`) are renamed to `project_id`; they already point at the boundary, only the name still says camp (Phase 1 §3.4).

**Store.** A physical outlet under one POS organization (`pos_stores.organization_id`, `backend/migrations/0010_pos_integration.sql:38-60`). A store is derived from the org, never from the camp (`SELECT id FROM pos_stores WHERE organization_id = ? LIMIT 1` — `backend/src/routes/pos/index.js:623-629`; Phase 1 §4a) and is NOT a tenant or project boundary: two stores of one tenant share one `pos_products.stock_quantity` number today (deduction `WHERE` holds `id + tenant_id + stock_quantity >= ?` with no `store_id` — `backend/src/routes/pos/index.js:646-648`; Phase 1 §4c). Under D1/D3 the store remains an outlet attribute on sale rows; per-project attribution lives on transaction and line-item `project_id` tags, never on the store row. (The question of whether the store row itself ever carries a `project_id` column is an escalated tension — see §12 Q1.)

**Guest — the two-worlds framing.** The guest is the customer identity and the anchor of the model. **Backend/admin world: modular project isolation.** Every admin/POS read and write carries the project dimension (from `resolveScope`'s extended scope, plugging in at `resolveScope.js:207-208`); staff see only their project's rows and each project reports its own P&L (closing Phase 1 gaps G6.1–G6.4). **Customer world: unified single tenant identity.** Per D2 the guest sees one storefront, one brand, one menu; per D3 the guest pays one bill — a single cart/order/payment header whose line items are tagged by `project_id` behind the scenes. A guest who books a camp room and charges restaurant dinner to the same bill (Phase 1 Q3) is therefore ONE order, not two: one tenant-grain header, camp lines and restaurant lines distinguished only by their tags. Isolation is airtight where staff operate and invisible where guests pay — that is the whole model.

## §3.5. Backfill and legacy behavior

> Covers only what §3 + §8 + §10 already decide: default-project provisioning for tenants with no explicit project at migration time; row-by-row fate of existing `order_items` / `pos_transactions` / `pos_organizations` rows (NULL semantics, which keep NULL permanently); and the per-family nullable-permanently vs enforce-after-backfill verdicts. No new mechanism; rollout numbering and gates live in §8 / §10.

- **Tenants with no explicit project at migration time — default-project provisioning rule.**
  - **Definition (unchanged from §3 conventions):** the tenant default project is the tenant's single live project, resolved by the same rule as `tenant-import.js:199-203` (`SELECT id FROM projects WHERE tenant_id = ? AND deleted_at IS NULL`; default iff exactly one row). Every §3 backfill source bottoms out at this default.
  - **Which tenants qualify for provisioning:** only tenants with **zero** live `projects` rows get a provisioned default project. Tenants with exactly one live project use that row (no new row, no data change to `projects`). This matters on staging as written: Phase-1 counts show `tenants` 3 vs `projects` 1, so zero-project tenants exist and the provisioning branch fires; all operational tables are 0 rows, so every backfill below is a staging no-op verifiable via the Ph0 per-table NULL-count done-signal (§10 Ph0).
  - **How the provisioned row is created (design shape, §8/§10 own the migration number):** one `projects` row per zero-project tenant, provisioned in the same additive window before any table backfill reads the default (i.e. a predecessor of 0100–0104, still inside Ph0 zero-customer-facing-change). Shape follows the existing schema defaults: `project_type = 'camp'` (schema default `0063:31`; `tenants.type` default `'camp'`), `status = 'active'`, `slug` derived deterministically from the tenant (tenant subdomain, uniquified per `UNIQUE(tenant_id, slug)` `0063:26-46`), `tenant_id` = the owning tenant. No branding/data copy: tenant branding stays on `tenants` (§3.2), the project row is an empty isolation anchor.
  - **Triage for multi-project tenants:** mechanical backfill takes the **oldest live project** and queues the remainder for admin triage (§3 conventions; §8 0100 source; §11 R1 mitigation). Concretely: every backfill statement that falls through to "→ tenant default project" binds the oldest-live id; a per-table orphan/NULL report lists every row that took the fall-through (the Ph0 done-signal: per-table NULL counts match the triage expectation, §10 Ph0); gates 0106/0107 abort visibly while triage is undrained (§8; §10 Ph1 ships gates as their own deploy, never bundled with UX). Staging tenants are 0-/1-row so misattribution only bites production — run the orphan report against a production snapshot first (§11 R1).

- **Row-by-row fate of existing rows (NULL semantics; which keep NULL permanently).**
  - **`order_items` (staging: 0 rows; §3 row 4, T+tags line tag):** ADD nullable `project_id` (0101) → backfill in **one statement from the parent order's project** — correct because today every line's project IS its parent order's project (§8 0101; §4.6). Chain for the parent: existing `orders.camp_id` → room's project (`reservations.js:335-350` binding) → tenant default project. NULL semantics: NULL = pre-project-era legacy row attributed via the parent order's project (§4.6 NULL-tolerant shape). **Permanence verdict: enforced NOT NULL via 0107 as §3/§8 are written** (row 4 path ends NOT NULL; 0107 lists `order_items` in the enforce set); the NULL→parent fallback survives only as a report-time convention for any orphan triage window, and the enforcement-vs-nullable tension is the open sub-point escalated to §12 Q2 (0107 assumes NOT NULL — confirm).
  - **`pos_transactions` header (staging: 0 rows; §3 row 6, T+tags header):** ADD nullable `project_id` (0103) → **best-effort** backfill from the first line-item product's `pos_products.camp_id`, falling through to the tenant default project where there are no lines (§8 0103 source). NULL semantics: NULL = **multi-project D3 payment** — one payment settling lines from several projects, so a single-project tag would be a lie. **Keeps NULL permanently by design** (§3 row 6 "keep nullable by design"; §8 0107 explicitly excludes `pos_transactions` from enforcement). Post-migration single-project payments may carry the tag; multi-project payments keep NULL and per-project attribution comes from the tagged `pos_transaction_items` lines underneath.
  - **`pos_organizations` (staging: 1 row; §2 row 12 bucket T):** **NO column, NO backfill, NO NULL semantics — row untouched.** D1 does not subdivide the 1:1 tenant root (addressed by PK, never tenant-predicated, `pos/index.js:62-63`; bridge via `tenant_org_mapping`). §3 tail lists it under "Tables gaining NO column"; §8 0103 adds columns to txn header/items/users/tables only. Same fate for its T-bucket siblings: `pos_stores` (1 row — attribution lives on transaction/line tags, store→project binding is convention-only per §12 Q1, no column) and `pos_shifts` (1 row — drawer spans projects; split comes from tagged transactions, never the shift row).
  - **For completeness (same fate pattern, §3 rows cited):** `pos_users` (1 row; row 8) → ADD nullable home-project tag (0103), backfill to tenant default, **floaters nulled in triage, keeps NULL permanently** (NULL = floater across projects, §3 row 8; §8 0107 exclusion). `promotions` (0 rows; row 14) → ADD nullable tag (0104), **existing rows keep NULL with no forced defaulting** (NULL = tenant-wide promo, all projects, §3 row 14; §8 0107 exclusion). `orders` header (0 rows; row 3) → ADD nullable (0101), backfill single-project rows via `camp_id` → room's project → default, **keeps NULL permanently** (NULL = multi-project D3 cart). All other P-family rows (rename-family + catalogue/food/POS-lines below) backfill to exactly one project and terminate NOT NULL.

- **Nullable permanently vs enforced after backfill — per-family verdicts (with reasons).**
  - **ENFORCED via gates (fail-closed; abort visibly if NULLs remain, no data change on success):**
    - **0106 family — rename-family + pre-existing column:** `rooms_new` (row 1), `rate_plans_new` (row 2), `meal_schedules` (row 12), `service_items` (row 15, column already exists). *Why enforced:* each row belongs to exactly one project by construction — a physical room sits in one camp-project (`camp_id → projects`, §3.3); a rate plan derives from its owning product's camp (`camps.js:972-979`); a meal schedule is the per-camp serving of a tenant meal (§4b); a service item is the D1 precedent shape already carrying literal `project_id` (`0072:20-32`). These are renames/formalizations of a camp-id that already pointed at `projects(id)`; NULL post-backfill can only mean a delete-orphan (`ON DELETE SET NULL`) or an untriaged row, so the gate must fail rather than silently admit it. Predecessors: 0100 (rooms/rate-plans/schedules) + 0104 (service-items NULLs).
    - **0107 family — single-owner P rows:** `meals` (row 10), `meal_categories` (row 11), `pos_products` (row 5), `pos_tables` (row 9), `inventory_adjustments` (row 13), `order_items` (row 4). *Why enforced:* D1 food/menu entities gain the boundary they never had (tenant-grain today, gap G6.2 — shared dishes are duplicated per project in triage, categories move with their meals); `pos_products` formalizes the soft `camp_id` TEXT that is already the room-type ownership source of truth (`0053:21-25,50-53`); dine-in tables belong to the restaurant project serving them; an adjustment ledger row touches exactly one product which has exactly one project (backfill via product); an order line has 1:1 attribution by construction (junction rejected, §4.6). Predecessors: 0101–0104. Known sub-point: `order_items` NOT NULL vs §4.6 NULL-tolerant semantics — see §12 Q2.
  - **NULLABLE PERMANENTLY by design (never gated; every report treats NULL as a legal value, §7.2 unassigned bucket):**
    - **`orders` header (row 3) — NULL = multi-project D3 cart.** *Why:* D3 mandates one cart/order/payment spanning camp + restaurant lines; purely project-scoped headers would force splitting one bill into N orders (rejected §4.5). Single-project orders may carry the tag; mixed carts keep NULL on the header with per-line tags underneath.
    - **`pos_transactions` header (row 6) — NULL = multi-project D3 payment.** *Why:* one payment settles lines from several projects; per-project headers would force one payment per project (same rejection as orders). Same header/lines split as the order leg.
    - **`pos_users` (row 8) — NULL = floater across projects.** *Why:* shared staff roster (§5 bullet 6, scoped by `organization_id` today) — one staffer works both projects, so pure project scope would duplicate floaters. Rows land home (tenant default) with floaters nulled in triage.
    - **`promotions` (row 14) — NULL = tenant-wide promo, all projects.** *Why:* tenant-wide promos ("10% off everything") legitimately span projects; pure project scope would duplicate one promo per project. Project-specific promos carry the tag; existing rows keep NULL preserved by design.

## §4. Unified storefront (D2 + D3)

### 4.1 Current guest flow (three disjoint carts, three order paths)

Entry points: tenant landing `/` (hero + rooms + reviews + map via `TenantLanding.astro`, tenant zone only); rooms section (`CampBooking.tsx` island); `/book` reservation page (`ReservationSummary.tsx` island, tenant-only ZoneGuard); `/menu` menu page (`TenantMenu.tsx` island, data from tenant-grain `GET /api/meals` with no camp predicate); `/storefront*` shop islands (`ShopCatalog`, `StorefrontCart`, `StorefrontCheckout`, `StorefrontConfirmation`, tenant-only per `routeZones.ts:68`, data from tenant-scoped `GET /api/storefront/products` plus session cart API).

The three carts are mutually unaware: (1) room reservation cart (`ReservationItem[]` in localStorage `sc_reservation`, no server row, no project tag); (2) menu cart (`CartItem[]` in localStorage `sc_menu_cart`, WhatsApp handoff only — writes zero DB rows); (3) shop session cart (server-side `carts` + `cart_items` keyed by per-tenant session UUID, product-only lines with no kind, schedule, or project tag).

### 4.3 The unified cart: one cart holding a room booking AND a dinner reservation

Every guest-selectable thing normalizes to ONE line grain — the money grain already proven by both writers (totals recomputed as quantity × unit price): kind + referenced id + `project_id` + name + quantity + unit price + total + optional schedule/fulfillment payload. Kinds: room-night (ref = room, quantity = nights, schedule = check-in/check-out/guests), dated-serving meal (ref = serving, quantity = covers, schedule = date/meal), stay-attached meal plan (ref = product, today's bridge shape), retail (ref = product, today's cart-item shape), service (ref = service item).

### 4.4 Cart-item `project_id` — PICK: YES, the cart line stores `project_id` directly

The server session cart line (extended with kind, reference, `project_id`, schedule payload) carries `project_id` on EVERY line, resolved at add-time and re-verified server-side from per-kind source tables: room lines from the room's owning project; dated-meal lines from the serving's project; meal-plan and retail lines from the owning project of the product (falling back to the tenant default project); service lines from `service_items.project_id` directly. Checkout then becomes a pure translate (cart line → order item copying the same tag) instead of a re-resolution pass; the stored tag freezes attribution at selection time so mid-session mapping changes cannot silently move revenue across P&Ls; per-project subtotals in the cart UI need the tag before checkout exists. The rejected alternative (resolve `project_id` only at checkout) doubles checkout reads, leaves pending carts un-attributable, and admits attribution drift between add and pay. Trust rule: the client may echo `project_id` for optimistic UI; the server ignores it and re-derives per line, rejecting foreign-tenant references.

### 4.5 Checkout — PICK: ONE order (N sub-orders rejected under D3)

Checkout creates exactly ONE `orders` row for the whole cart — room nights, dinners, retail, and services together — with one typed `order_items` row per cart line (each carrying its `project_id`), followed by exactly ONE Paymob intention for the grand total on the single order reference, confirmed by the existing HMAC webhook. Flow: validate all lines server-side in one pass (room overlap guard moves with the unified insert unchanged; stock conditional deduction; schedule capacity; same-tenant re-verification of every line's project); insert ONE `orders` row (stay fields set from the room lines; a cart with NO room line carries NULL room/dates and fires no stay side effects); insert all `order_items` rows with `project_id` in the second batch (two-batch ordering: items only after the guarded insert succeeds, since D1 has no conditional abort); fan out fulfillment mirrors per line kind reading the stored tag (kitchen `pos_transactions` rows as today; room-status effects) — these are effects, not orders, and carry no payment; create ONE Paymob intention (grand total), persist the intent id on the order, return the client secret; webhook capture flips the ONE order to paid.

N sub-orders (one per project) is rejected: under LOCKED D3 it is not available, and independently it fails on the merits — single payment becomes impossible (N intentions, N reconciliations, split-tender compensation that does not exist); it recreates the exact orders-duality the audit documents as the problem; linkage would need a parent-order mechanism (the allocations problem moved up one grain with worse atomicity); the guarded room insert (409 overlap) and the single-reference guest confirmation both assume one order row per purchase. Therefore no N-linkage mechanism is designed.

Transition note (schema ownership in §3/§8, not designed here): `storefront_orders` / `storefront_order_items` remain the live shop-only path until the unified checkout ships; migration/aliasing of historical shop rows is a §12 Q4 decision.

### 4.6 Line-item mechanism — PICK: ADD the column to `order_items` (allocations table rejected)

**PICK: direct `project_id` column on `order_items`.** Attribution is 1:1 per line by construction (each cart line belongs to exactly one project), so a junction buys nothing — junctions exist for many-to-many splits and there is no split here. Per-project P&L becomes a direct line-grain aggregation with no extra join; the existing report patterns port over with a single added grouping term. Backfill is a single statement from each line's parent order project (correct because today every line's project IS its parent order's project). NULL semantics stay clean (NULL = pre-project-era legacy row attributed via the parent) under the same orphan convention as the existing nullable project FKs. The write path stays single-batch (one extra bind value per row instead of doubled statements). This matches the codebase's own direction: the only existing line-level project columns are direct columns, not side tables. The rejected `order_project_allocations` side table is justified only for split-revenue lines, which D3 excludes by definition.

## §6. POS & stock isolation — PICK: Option Y (one org per tenant, one store per project)

### 6.1 Current mechanics (decided context)

Mapping is 1 tenant : 1 POS org (`tenant_org_mapping` with unique tenant and org sides); provisioning (`ensureTenantOrg`) looks up the mapping, inserts the org by slug, resolves its id, inserts one store, inserts the mapping. POS login credential lookup is org-blind, then resolves org→tenant via the mapping. The POS token carries tenant, org, store, role claims — no project claim. The `posAuth` gate enforces realm, rejects refresh-type tokens, and re-checks staff active status. Store resolution in the sale handler falls back from the cashier's store to the org's first store to a literal. Stock is one integer per product row (per-store tables stay dropped); the deduction guard has no store predicate, so two stores of one org share one stock number. Inventory reads split predicates (low-stock by org, adjustments/reorder by tenant) — safe only because product create dual-writes both 1:1. The POS realm carries no project axis on org/store/user/transaction rows; the product→project link exists only as the soft `pos_products.camp_id` source of truth, and product creation already requires it on multi-project tenants.

### 6.2 Option X vs Option Y — PICK: Y

**Option X — multiple orgs per tenant (one org per project)** — requires breaking the UNIQUE-backed 1:1 mapping, redefining it as 1:N, reworking the single-row provisioning assumption and all single-org consumers; billing/reporting keyed per-tenant, tax/timezone lookups per-org, and dual-column product writes all fork; one logical SKU becomes N rows with divergent stock, breaking the products mirror and the meal-plan bridge guard.

**Option Y — one org per tenant, one store per project; product scoping by project** — keeps the 1:1 mapping untouched and provisioning unchanged except provisioning N stores (one per project) instead of one. Store is already the org-child transaction stamp; making the store the project boundary aligns with the existing store-id token claim and the org-store resolution site. Product→project ownership already exists; Y only enforces it in POS/stock paths instead of inventing it.

**PICK Y, without hedging:** X breaks a UNIQUE-backed 1:1 contract plus provisioning and ~8 consumers while Y breaks nothing; Y scopes the existing single-integer stock by the existing owner column while X duplicates product identity across orgs and forks every stock reader; Y reuses the store-id claim already in the token while X needs org disambiguation at login (the org-blind lookup cannot pick among N orgs without new UX + claims); Y converges both inventory legs onto one predicate family while X widens the split.

### 6.3 POS auth impact under Y (token impact)

The token gains a `projectId` claim (the project bound to the cashier's store) alongside the existing org/store claims; tenant resolution via the mapping is unchanged; the project value is resolved store→project with the store record authoritative and the claim a cached copy. Login keeps the org-blind credential lookup, then resolves the cashier's store to its project and embeds it in both access and refresh claims. Cashiers with NULL store today silently inherit the org's first store — that fallback is REMOVED; null-store login returns a project-assignment error and forces explicit assignment. Store selection becomes a required UX step: single-store cashiers get no picker (bound store's project is implicit); multi-store/null-store cashiers get an explicit project/store picker at login, with mismatched picks rejected. Refresh re-resolves BOTH dimensions from the database (tenant via the mapping as today, plus project via fresh store→project lookup) and never trusts the stale claim alone — changed or removed bindings re-issue corrected claims or fail closed. Per-request enforcement keeps the existing signature/realm/active checks and adds a project-equality guard on write paths; the dual-realm shared branch surfaces the project the same way so shared routes can enforce it.

### 6.4 Stock isolation mechanics under Y

The per-project quantity lives in the existing `pos_products.stock_quantity` integer, with one product row per logical-SKU×project distinguished by the live project-owner column (the `project_id` rename lands with a later locked-schema window — until then the camp-id column IS the project column). No per-store table is recreated; the store never owns stock, the project does. The deduction guard and ingredient pre-read both gain the project predicate — a cross-project sale attempt then misses the predicate and fails with the existing product-not-found error (correct isolation error, no new code path); the race-compensation path is unchanged. The low-stock read swaps its org predicate for the tenant+project predicate (dropping the mapping pre-lookup on this path); adjustments guard/update/re-read and reorder suggestions gain the same project predicate, with adjustment rows additionally stamping the project. Dual-column cleanup: `organization_id` stops being a stock-read dimension entirely and remains only as the org-identity stamp on writes and the tax/timezone owner; tenant + project become the single stock predicate family across sale, low-stock, adjustment, and reorder paths.

### 6.5 Terminal-to-project binding

Source of truth is the store record, not the token: each store row binds to exactly one project (locked-schema: convention binding via store code ↔ project slug until a column window opens; the resolver validates against live projects with the same guard shape as the existing same-tenant checks). The token's project claim is a cached copy for fast query guards. Resolution order per request: cashier store → store (project binding) → project. Login/refresh materialize it into the claim; write paths re-verify cheaply (the product predicate does this implicitly; the transaction store must be bound to the claim's project, replacing the silent first-store fallback with a required store + rejection on null or cross-project). Mismatch policy: claim-vs-record disagreement fails writes closed, refresh re-issues corrected claims, reads degrade to the record's project never the claim's.

Services/typed inventory: `service_items` (the only table with a literal project column today — the D1 precedent pattern) plus `project_items`.

### 7.2 The GROUP BY project query shapes (design shapes, post-design)

Four shapes, each described by grain + grouping key + window, following existing report precedents: (1) accommodation revenue per project — order-header grain grouped by the header's project, summing order totals and counting orders over the tenant+date window excluding cancelled, following the existing by-camp series shape that is computed but dropped by the panel today; (2) line-level revenue per project — the D3 key — order-item grain grouped directly by the line's `project_id` tag (tenant scope via the parent-order join), summing line totals and counting lines, which ports the existing grouped-revenue shape over unchanged with only the grouping target moved from the header to the line tag; (3) POS revenue per project — transaction-item grain joined through transactions and products, grouped by the product's project, summing quantity×unit price and counting distinct transactions excluding voided, following the existing revenue-by-product-type join shape with the grouping key swapped to the product's project; (4) combined per-project P&L — an application-level union of the three legs (accommodation revenue, POS revenue, order/transaction counts per project) with an explicit unassigned bucket for NULL-project rows (FK orphan convention) so nothing is silently dropped.

### 7.3 Combined tenant P&L — VERDICT: UNCHANGED (existing endpoints byte-identical, new endpoint additive)

The tenant aggregate is exactly the sum over projects, so every current endpoint (revenue summary, revenue breakdown, seasonal, super-admin per-tenant aggregates) stays byte-compatible. `GET /api/reports/profit` is additive; its footer row (SUM over the per-project rows) must equal the existing tenant aggregate for the same window — that equality is the acceptance check. The only delta: the unassigned bucket (NULL project after project delete) is listed explicitly instead of being silently included, so combined P&L reconciles to the cent.

### 7.4 Cross-project customer view (room + dinner, same customer)

Today NO join key exists between the two legs: the booking leg joins `orders.customer_id → customers(id)` with customer metrics counted from those tables; the POS leg's `customer_id` column exists in DDL but the sale handler never writes it (the string "customer" appears nowhere in the POS routes) — POS sales are anonymous at the data layer; the two CRM tables (`customers` vs legacy `pos_customers`, already direction-planned as replaced-by-`customers`) coexist. After the design the join key is `customers.id`, written into `pos_transactions.customer_id` at checkout: no storage change needed (column + FK exist), identity resolution reuses the booking find-or-create verbatim (email-first, phone-second, update-or-create), with POS checkout capturing email/phone (or a room-charge reference carrying the booking's customer id) and stamping the resolved id. Until POS stamps it, the cross-project view is a UNION grouped by normalized email/phone with an explicit anonymous-POS-sales caveat row — never a fabricated join; `pos_customers` remains read-only legacy. Report shape: per-customer rows (accommodation revenue from orders, POS revenue from transactions, plus the project list per customer — the project list is what makes it cross-project rather than just cross-table).

## §11. Top-5 risks + mitigations

1. **Backfill misattribution (P&L correctness).** Tenant-default-project backfill silently assigns rows to the wrong project on multi-project tenants → per-project revenue wrong from day one. *Mitigation:* oldest-live-project + explicit admin triage queue; per-table orphan/NULL reports as the Ph0 done-signal; gate every NOT NULL enforcement (0106/0107) on triage drain; staging tenants are 0-/1-row so this only bites production — run the orphan report against a production snapshot first.
2. **Checkout atomicity regression (D1 batch limits).** Moving the guarded room insert (conditional-overlap → rejection) into the unified insert risks double-booking if the two-batch ordering is broken. *Mitigation:* keep the §4.5 two-batch shape (guarded order insert, items only on success — D1 has no conditional abort); concurrency test for overlap-rejection under the unified path before Ph4 ships.
3. **Stock-guard predicate change blocks legitimate sales.** Adding the project predicate to the deduction guard turns mis-scoped products into product-not-found errors at the till. *Mitigation:* Ph2 ships predicates only after the 0102 backfill audit; pre-rollout product-scope report (every product row has exactly one project); staging sale matrix (same-project OK / cross-project rejected) as the Ph2 gate.
4. **Null-store cashier lockout.** Removing the first-store fallback rejects every cashier with NULL store at next login. *Mitigation:* assignment sweep (every staff row gets an explicit store) as a Ph2 entry criterion; ship the store-picker UX in the same deploy as the rejection (never before/after); keep a super-admin reassign path.
5. **Single-Paymob-intention cutover.** One intention on the unified reference replaces two working payment paths; webhook mismatch or partial capture strands paid/unpaid state with no split-tender compensation. *Mitigation:* keep the shop-orders path live in parallel through Ph4 (no flag-flip); sandbox end-to-end (mixed cart → one intention → webhook → ONE paid order) as the Ph4 gate; failure leaves the single order unpaid (retry), never half-paid; extend the webhook order-match before, not with, the traffic switch.
