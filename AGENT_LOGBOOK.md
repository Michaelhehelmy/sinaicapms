## Persistent Learnings & Codebase Gotchas

*This section lists persistent lessons, structural details, and API quirks discovered by agents during development. Update this list as you find new gotchas.*

- **D1 rejects TEMP tables in migrations (2026-08-24)**: wrangler `d1 migrations apply` fails with `not authorized: SQLITE_AUTH` on `CREATE [TEMPORARY] TABLE` — the D1 authorizer blocks temp tables both locally AND in production workerd. Dead-code temp-table blocks in migration files are landmines; delete them.
- **Migrations must match the real lineage (2026-08-24)**: 0061–0066 were committed against an imagined schema (columns/tables that don't exist per the actual ledger) and could never apply anywhere. Before writing a migration: check `npx wrangler d1 migrations list --local` (and `--remote`) + `pragma_table_info` on BOTH environments — local and prod can diverge silently. A trigger referencing a nonexistent column (e.g. old `trg_camps_updated_at` → `camps.updated_at`) doesn't break creation but fails EVERY subsequent UPDATE at runtime. Table-rebuild migrations must recreate ALL pre-existing indexes or they vanish (0066 initially dropped the orders availability composites).
- **Response helper signatures (2026-08-25)**: `jsonResponse(data, status)` and `errorResponse(message, status, errors)` — NEVER pass the Hono context `c` as first arg. services.js had this systematic bug across 20+ endpoints. `validationError(parsed, status)` takes the Zod safeParse result, not `(c, parsed.error)`.
- **order_items has no tenant_id (2026-08-25)**: The table only has: id, order_id, type, reference_id, name, quantity, unit_price, total_price, created_at, split_group, course_number, course_status. Tenant isolation is via `order_id` → `orders.tenant_id` FK. Never filter order_items by tenant_id.
- **D1 atomic patterns (2026-08-25)**: Use `DB.batch()` for multi-statement atomicity. Use `WHERE col + ? >= 0` guards for stock/concurrency. Use `INSERT ... SELECT WHERE NOT EXISTS` for race-safe inserts. D1 has no conditional abort between batch statements.
- **Tenant-scope precedence (2026-08-30, B1)**: `camps.js` (and any drill-down–aware module) resolves request tenant as: REAL tenant admin's own `user.tenantId` ALWAYS wins (cannot escape via `x-tenant-id` hint) → marketplace-scoped super admin honors an EXPLICIT real-tenant scope hint (TenantDrilldown) → else marketplace directory (scope hint or `'marketplace'`). Implemented once in `resolveTenantId(user, scopeTenantId)` at camps.js:133 and used at ALL 5 resolutions (GET ×2, POST, PUT, DELETE). PUT/DELETE keep the `isMarketplaceTenant(tenantId) && user?.role==='super_admin'` owning-tenant resolution branches (only fire when no real tenant scope is effective).
- **`cachedJsonResponse` MUST vary on `x-tenant-id` (2026-08-30, B2)**: `Cache-Control: public, max-age=300` with no `Vary` means the browser AND the Cloudflare CDN key by URL alone → tenant A's response gets served to tenant B for identical URLs (verified cross-tenant leak). response.js now sets `Vary: x-tenant-id`. `jsonResponse` stays `no-store`. Same-URL/same-header "stale response" assertions still need spec-level `page.route('**/api/v1/camps')` cache busters.
- **wrangler dev crashes under sustained E2E load (2026-08-30)**: local `npx wrangler dev --port 8787 --local` (miniflare workerd) dies after ~15–17 minutes of continuous Playwright traffic (no error in log — it just stops; ports go dead). Symptom: mid-run `TypeError: fetch failed` at `apiRequest` login + waves of `content-area` 10s waits + mass cascades. The full 218-test `--project=admin` local gate CANNOT reliably finish in one shot. Mitigations: run targeted specs (<10 min) on warm servers; warm with curl login + `GET /api/camps` + `GET /admin`; use `setsid ... </dev/null >log 2>&1 &` to keep dev servers alive across tool sessions; when a run dies, KILL orphaned `workerd` processes before rerunning (they wedge — accept TCP, never respond → `UND_ERR_HEADERS_TIMEOUT`). CI (fresh DB, workers=1, retries=2) is the real full-gate environment.
- **E2E test data pollution (2026-08-30)**: `playwright.config.ts` has ONLY `globalSetup` (creates a test tenant + admin per run) and NO `globalTeardown` → every run leaks tenants/admins; killed runs leak more. ~70 tenants + 49 admins accumulated. `/api/admin/tenants` and `/api/admin/admins` are PAGINATED (pageSize default 50) → seed rows (acaciacamp) fall off page 1 and DOM-content assertions (`content.toContain(email)`) break at scale. Purge runbook (dev D1 sqlite at `backend/.wrangler/state/v3/d1/miniflare-D1DatabaseObject/*.sqlite`): delete tenants except `acaciacamp`/`michaelshouse`/`marketplace`, delete `admins` NOT IN (`admin@sinaicamps.com`,`e2e-admin@test.com`) AND email LIKE e2e-%/iso-%/double-%/edge-%/crud-%/lifecycle-%/diag-%, delete their `projects`. State-dependent spec known-fragile on a truly clean DB: `crud-execution.spec.ts:33` "no create button for tenant with existing camp" relies on leftover camps pollution; it targets TEST_TENANT (acacia), which HAS camps — it fails only when the backend is down/empty-state renders.
- **Marketplace camps directory groups by tenant (2026-08-30)**: `GET /api/camps` cross-tenant (marketplace) SELECT is `... GROUP BY c.tenant_id` (one row per tenant); the tenant-scoped SELECT returns ALL of that tenant's projects. Directory presence assertions must not expect every project of every tenant.
- **`throwOnError` + `showToast` = super-admin render-loop crash (2026-08-31, T3 admin sweep) — FIXED by T5**: In `app/src/hooks/useQueryHooks.ts`, `useErrorToast()` calls `showToast(...)` (a setState on the Toast provider), and ~90 report query hooks invoke it from TanStack Query v5 `throwOnError: (err) => { toastError(...); return false }`. `throwOnError` runs during the query-observer RENDER phase, so on any error this is a `setState` during render on a different component → React "Cannot update a component while rendering a different component" → infinite sync-re-render loop → chromium dies (`There was an error during concurrent rendering...` repeated). Triggered specifically by the tenantless SUPER admin (admin@sinaicamps.com) hitting tenant-scoped report endpoints that 400 for no tenant (e.g. `/api/v1/reports/kitchen-performance`), so `/admin/analytics`, `/admin/storefront`, `/admin/billing` crash the browser for super admins only. Tenant admins render those panels fine. To test those admin panels in a mobile audit, log in as `e2e-admin@test.com`/`TestPass123!` (tenant admin), NOT the super admin. **FIX (T5, single shared change in `useErrorToast`)**: wrap the `showToast(...)` call in `setTimeout(() => {...}, 0)` — deferring the setState out of the render phase to the next macrotask. Because the toast helper is shared by BOTH query `throwOnError` AND mutation `onError`, the whole app now defers error toasts by one tick, which is harmless in production. Trade-off for tests: any test that asserted a `useErrorToast`-driven toast synchronously after `await waitFor(isError)` (or after a rejected `mutateAsync`) must wrap its toast assertion in `waitFor` (made the mutation error assertions + query error-toast assertions async-aware in `useQueryHooks-extra*.test.tsx` and added a dedicated "render-phase toast deferral" regression test). `useApiError.ts` is dead code (imported nowhere) and was NOT touched, so `useApiError.test.ts`'s synchronous `showToast` assertions remain valid.

- **tenant-import binds `project_id` on every project_id-bearing INSERT (2026-09-30, DEFECT-1)**: `runImport` in `backend/src/api/tenant-import.js` resolves ONE `resolvedProjectId = projectId || defaultCampId || null` (the DEFECT-3 project block's value → the tenant's sole live project → NULL) and binds it in all six inserts that own the column: `pos_products`, `rooms_new`, `rate_plans_new`, `meal_categories`, `meals`, `pos_users`. NULL degrades gracefully, never throws — every target column is nullable at head 0124. Tables the import does NOT write (`products` mirror, `meal_lang`, `meal_categories_lang`, `meal_schedules`) have no project_id column by design (0108 header: translation rows follow parents). **Schema history that explains the confusion**: 0107 made `project_id` NOT NULL on pos_products/rooms_new/rate_plans_new/meal_categories/meals (0108 added fail-closed NULL guards); **0111 rebuilt all five back to NULLABLE** because `project_id TEXT REFERENCES projects(id) ON DELETE SET NULL` and `NOT NULL` contradict (deleting a project would abort). `pos_users.project_id` was never NOT NULL (0100 nullable + partial index 0107). A DB stranded at 0107–0110 (the local miniflare D1 sat at `0110_create_payment_records` with NOT NULL on all five) therefore 500s the whole import on a NULL bind — that schema's intended fail-closed behavior, and the very reason the local round-trip probe in A.6 reported `NOT NULL constraint failed: pos_products.project_id` instead of a silent NULL. Always check `PRAGMA table_info(<t>).project_id.notnull` on the DB you are testing against before reasoning about NULL tolerance.
- **Manifest example fixtures carry target-tenant placeholders that FK-fail on a fresh DB (2026-09-30)**: `docs/examples/manifests/*.json` (A.4) intentionally include `campId`/`categoryId`/`storeId`/`mealCategoryId` placeholders that name ANOTHER tenant's rows — the files' own `_note` says they "must match the target tenant (or be omitted)". With FK enforcement ON (as in D1 and in a better-sqlite3 replay with `PRAGMA foreign_keys = ON`), importing them unmodified fails: a stale `campId` trips `rooms_new`/`rate_plans_new` FK guards, and `meals.meal_category_id` is NOT NULL so a stale `mealCategoryId` aborts the meal batch. Strip those keys (and any `identity` block, which selects the super-admin creation mode) in any test that replays a manifest against a locally-seeded tenant. See `backend/tests/tenant-import-project-id.test.js` `loadManifest()`.
- **Replaying every migration into better-sqlite3 gives a real fresh D1 (2026-09-30)**: `readdirSync(migrationsDir).filter(f => f.endsWith('.sql')).sort()` + `db.exec(readFileSync(...))` in order replays the full 0001_core → 0124 lineage into `:memory:` with FK enforcement ON — the cheapest way to test against the REAL post-rebuild column lists and constraints (several tables were rebuilt by 0107/0111/0112/0115/0123, so hand-written stub DDL drifts). Wrap with the repo's thin D1 adapter (`prepare().bind().all()/first()/run()` + `batch()` in a `db.transaction`) — see `backend/tests/price-overrides.test.js`. Beware: migrations that require pre-existing DATA (0107/0111/0112 plain-INSERT fail-closed gates) replay fine on an empty DB because their guards are vacuous, and better-sqlite3 allows `PRAGMA foreign_keys = OFF` where D1 does not (D1 needs `PRAGMA defer_foreign_keys = true`) — enable FKs in the test and let each file manage its own pragma.
- **`GET /api/products` must SELECT `p.type`, or export silently downgrades every product to `retail` (2026-09-30, DEFECT-2)**: the column exists (`0107:150` `pos_products.type TEXT CHECK(room|menu|buffet|retail) DEFAULT 'retail'`) and the import side already accepted it (`tenant-import.js` Zod `:106` optional enum + INSERT binds `item.type || 'retail'`), but the products list SELECT (`camps.js` `productsRoutes.get('/')`) omitted it from both the SELECT list and the row map. `scripts/export-tenant.mjs` only emits `type` when the GET returns it, so a manifest exported from a live tenant carried no `type` and re-import defaulted every product to `retail` — a `room` product round-tripped as `retail` with exit 0 on BOTH ends, i.e. the loss was invisible to the operator. Fixed by adding `p.type` to the SELECT and `type: p.type ?? null` to the mapping. **Read-side SELECT lists are the export contract**: any column an exporter may need has to be named explicitly, because the response is built from a hand-written projection (`finalResults`), not `SELECT *`. `type` is single-word so `toCamel` passes it through unchanged — camelCase wire, no snake_case leak (unlike `base_price`/`short_description` in the same row).
- **`pos_products.sku` USED TO be UNIQUE GLOBALLY — FIXED by 0126 (2026-09-30)**: `sku TEXT UNIQUE NOT NULL` (0004:65, re-asserted by every `pos_products` rebuild through `0112:153`) was NOT scoped by `tenant_id`, and the import handler falls back to `'PROD-' + pid.toUpperCase()` when the manifest omits `sku`. Consequence while it held: replaying an exported manifest into a DIFFERENT tenant while preserving the source `sku` was a `SQLITE_CONSTRAINT_UNIQUE` violation, not a type/field assertion. **Migration `0126_tenant_scoped_unique_sku_email.sql` replaced it with `UNIQUE INDEX idx_pos_products_tenant_sku_unique (tenant_id, sku)`** (same for `pos_users.email` / `pos_users.username`), so overlapping manifests now import into as many tenants as you like. What is STILL globally unique and must still be stripped in a cross-tenant fixture: `pos_products.id`, `pos_products.barcode` (manufacturer-assigned — deliberately left global), `meals.id`, `rooms_new.id`, `rate_plans_new.id`, `projects.slug` (`UNIQUE(tenant_id, slug)`), and the `campId`/`categoryId`/`storeId`/`mealCategoryId` placeholders from A.4.
- **CLI exporters ending in `main()` are not importable — mirror their mapping and pin it with a drift guard (2026-09-30)**: `scripts/export-tenant.mjs` executes `main()` at module scope, so a unit test cannot import its transform. The pattern that works: copy the mapping into the test file verbatim (here `pick()` + the key list + the conditional `type` passthrough + `campIds[] → singular campId`) AND add a test that greps the script source for the key lines it duplicated. Without that guard the suite silently tests a mapping that no longer runs in production. Also assert the script no longer advertises the fixed defect in its header — a stale `KNOWN LOSSES` line is a lie the next agent will read.
- **A column in a `SELECT *` is still LOST-ON-IMPORT if the import never writes it (2026-09-30, DEFECT-4)**: `rooms_new` has `room_status TEXT DEFAULT 'available'` and `cleaning_status TEXT DEFAULT 'clean'` (0003:43-44, re-asserted by every rebuild through `0115:90-91`), and `GET /api/rooms` returns BOTH (`camps.js:760` `SELECT r.*`). But the tenant-import Zod `rooms` object had no such fields and the INSERT named neither column, so the DB applied its defaults on every row: a manifest exported from a live tenant silently reverted every room to available/clean, exit 0 on both ends — the read side looked perfect the whole time. **Read-side availability proves nothing about write-side fidelity; a round-trip is only closed when BOTH the SELECT and the INSERT name the column.** The two enums have different authority and must not be written the same way: `cleaning_status` is CHECKed by the schema (`IN ('dirty','in_progress','clean','inspected')`, 0003:44) so the Zod enum must MATCH it exactly — anything wider is a 500 from the DB and anything narrower is a silently rejected valid value; `room_status` has NO CHECK, so its enum is a policy choice and the correct source is the value list the admin endpoint actually writes (`camps.js:952` PATCH `/rooms/:id/status` = `available|reserved|occupied|cleaning|out_of_service`, and `orders.js:488` ROOM_STATUS_BY_ORDER_STATUS = the subset `reserved|occupied|cleaning`). Bind `room.room_status || 'available'` / `room.cleaning_status || 'clean'` so an omitted field writes the same value the column default would have — never pass `null` explicitly, which would defeat the DEFAULT and store NULL instead. Append new columns AFTER the existing ones in the INSERT: `project_id` is asserted at bind index 12 by `tenant-import.test.js` PROJECT_BIND and every pre-existing bind index in `tenant-import-smoke.test.js` `INSERT_COLUMNS.rooms_new` is positional, so inserting mid-list silently re-points those assertions at the wrong values.
- **Tenant-scoped uniqueness for import-written columns (2026-09-30, D3 / migration 0126)**: `pos_products.sku`, `pos_users.email` and `pos_users.username` are arbitrated by `idx_pos_products_tenant_sku_unique` / `idx_pos_users_tenant_email_unique` / `idx_pos_users_tenant_username_unique` — `(tenant_id, …)` UNIQUE INDEXes, NOT inline `UNIQUE` column constraints. Naming matters: a test that wants the import to load the same catalog twice must NOT strip `sku`/`email`/`username` (only the still-global `id`s + `barcode` + `campId`). `pos_products.barcode` is intentionally left globally unique (EAN/UPC is manufacturer-assigned, so two tenants legitimately scan the same packaged SKU). `pos_users.tenant_id` is NULLABLE, and SQLite treats NULLs as distinct inside a UNIQUE index, so legacy NULL-tenant rows are not covered by the arbiter — every pos_users read path is by `id`/`organization_id`, so that is consistent, but a NULL-tenant row can no longer be rejected as a "global duplicate". Any future migration that needs to re-scope one of these columns must rebuild the table again (SQLite cannot drop an index-backed constraint) and must re-apply the full 0111 idiom.
- **`meals.id` is the GLOBAL primary key, and it is the `meal_lang` join key (2026-09-30)**: `meals` is NOT rebuilt with a tenant-scoped id — a PK cannot be made composite without rewriting every `meal_lang`/`meal_schedules` reference. The import therefore generates a RANDOM `meal_<12 hex>` id (`crypto.getRandomValues`, not `crypto.randomUUID().slice()`, same width) and, when a manifest carries an explicit `meals[].id`, PROBES the owners first (`SELECT id, tenant_id FROM meals WHERE id IN (…)`) and answers cross-tenant with a clear 400 and same-tenant with a clear 409 — never a raw UNIQUE/PK error. Prefer this probe idiom over relying on the constraint for ANY explicit id in a manifest (`products[].id` still falls through to the generic 409 today; that is a deliberate remaining gap, not an oversight).
- **`PRAGMA defer_foreign_keys` needs a real transaction in a better-sqlite3 migration replay (2026-09-30)**: D1 wraps each migration file in a transaction, so the 0111 idiom's `PRAGMA defer_foreign_keys = true` … `false` bracket survives the whole file. better-sqlite3's `db.exec(sql)` runs in AUTOCOMMIT — each statement is its own implicit transaction, so the pragma is reset immediately and a data-bearing rebuild fails with `FOREIGN KEY constraint failed` on the parent DROP. Always `db.transaction(() => db.exec(sql))()` when replaying a rebuild migration (and set `foreign_keys = ON` BEFORE the transaction — it is a no-op inside one). `backend/tests/tenant-scoped-uniqueness.test.js` `execMigration()` is the reference helper.
- **`PRAGMA table_info` HIDES generated columns — use `table_xinfo` (2026-09-30)**: `pos_products.profit_margin` and `pos_users.name` are `GENERATED ALWAYS … STORED`, and `table_info` omits them entirely (`sqlite_master.sql` still shows them). A "column order is preserved" assertion written with `table_info` therefore silently skips the very column whose position is most fragile (`pos_users.name` sits between `updated_at` and `tenant_id`, right after the `datetime('now')` defaults). Compare `table_xinfo` (the GENERATED columns come back with `hidden = 3`) before and after any table rebuild. Related: the `profit_margin` expression does INTEGER division when both operands are stored as INTEGER (`40/100` → `0`), so probe it with REAL literals (`40.5`/`100.0`) — a `0` there is the SQLite type system, not a broken generated column.
- **The D1 free tier has a DAILY row-read limit that silently blocks remote census queries (2026-09-30)**: after a handful of `wrangler d1 execute <db> --remote --command "SELECT …"` probes the account returns `Your account has exceeded D1's free tier daily row read limit … [code: 7500]`. Every further remote read — including the rest of a duplicate census — is impossible until midnight UTC. Budget remote probes: batch every census counter into ONE `SELECT` with scalar subqueries (`SELECT (SELECT COUNT(*) …) AS a, (SELECT …) AS b`), because a compound `UNION ALL` SELECT is itself capped (`too many terms in compound SELECT`). Do the bulk of the verification locally (replay the migration lineage into better-sqlite3) and spend remote reads only on the production counts that decide whether a migration is fail-closed-safe.
- **Identity-mode tenant import is a SAGA; only that mode may be rolled back (2026-10-02)**: `POST /api/tenants/import` with an `identity` block commits a SHELL first (tenants, admins, POS org + store + tenant_org_mapping, default project) and only then runs `runImport`. The handler therefore keeps an undo log (`created`, threaded `runImport` → `importTenantManifest(env, tenantId, payload, created)`) and on any failure replays it in REVERSE order, best-effort per step, answering `500 Import failed: <reason>. All partial data has been rolled back. You can retry with a corrected manifest.`. Three invariants make it correct: (1) each entry is pushed only AFTER its INSERT resolves, and each `runImport` section pushes `{ table, column: 'tenant_id', value }` AFTER committing — a brand-new tenant means every row carrying that `tenant_id` IS this request's work, which is what makes the tenant-scoped delete exact instead of approximate; (2) an EMPTY log returns the caller's own precise 4xx/409/500 response unchanged (nothing was written, so there is nothing to undo) and a rethrown pre-write error keeps the outer catch's UNIQUE→409 contract; (3) **existing-tenant mode passes no log and NEVER deletes** — its thrown-error path answers `500 Import failed: <reason>. Partial data may remain in the tenant. Re-run with the same manifest to retry, or clean up manually.` instead. The reverse order is not cosmetic — it is dictated by the real FK actions at the 0126 head: `pos_users` →(NO ACTION) `pos_stores`/`pos_organizations`, `rooms_new` →(RESTRICT) `pos_products`, `pos_stores` →(NO ACTION) `pos_organizations`, `projects` →(NO ACTION) `tenants`, `admins` →(SET NULL) `tenants`, and **`pos_products` has NO FK to `tenants` at all** (only `project_id SET NULL`), so it would silently survive a tenant delete as an orphan. Read the edges with `PRAGMA foreign_key_list(<t>)` before writing any delete list — `pos_users` is the LAST section, so no handler failure can leave rows to exercise its edge today; it is logged anyway, because dropping it would break the store/org deletes the day a section is appended after it.
- **A better-sqlite3 D1 shim whose `batch()` awaits `run()` swallows failures (2026-10-02)**: the repo's thin adapters define `run: async () => ({ meta: { changes: stmt.run(...).changes } })` and then call `statements.map(s => s.run())` inside `db.transaction`. If the underlying `stmt.run()` throws, it rejects a PROMISE inside a synchronous `.map`, so the transaction COMMITS with nothing written and the handler's `await batch()` never sees an error — the request answers **success** while the injected failure surfaces later as a vitest "Unhandled Rejection". That produced a rollback test that reported `201` for a manifest whose meal rows were never written. Fix: keep `{ sql, params }` on the bound statement and have `batch()` execute them SYNCHRONOUSLY (`statements.map(({ sql, params }) => fire(sql, params))`), so a mid-batch failure propagates as a synchronous throw, the transaction rolls back, and the awaited rejection is catchable. Related: **the migration replay seeds rows** (a `superadmin` admins row among others), so never hardcode expected row counts in a fresh-replay assertion — snapshot a per-table baseline before the request and assert the count returns to it (for the tables that must be empty, assert the baseline itself is 0). **The same `{ sql, params }` requirement bites from the other direction too (2026-10-02, A1)**: a shim whose `bind()` returns only `{ all, first, run }` leaves `batch()`'s `statements.map(({ sql, params }) => …)` destructuring `undefined`, so the tape recorder throws `Cannot read properties of undefined (reading 'replace')` and the request answers 500 for EVERY batched section. It reads like a handler defect (and it made the identity suite red on all six cases at once) when it is a harness bug — check the bound-statement shape before believing a 500.
- **The identity saga's "was anything written?" test could not see a rejection raised INSIDE `runImport` (2026-10-02, A1 → FIXED by A2, same day)**: `tenant-import.js` decided "keep the caller's precise 4xx" vs "roll back and answer 500" with `created.length === 0`, which is only true for rejections raised BEFORE the shell's first INSERT (identity zod schema, subdomain format, subdomain uniqueness, admin-email uniqueness — exactly the four the rollback suite pins). Every DETERMINISTIC rejection raised inside `runImport` runs after six committed INSERTs, so the log is already populated and the wrapper rewrote it into `500 Import failed: <reason>. All partial data has been rolled back.`: the `products[].campId` pre-flight 400, the `menu.meals[].categoryName` pre-flight 400 (measured in `tenant-import-identity.test.js` M2), the rooms / rate-plan "unknown product" 400 and 404, the same-tenant duplicate meal id 409, the manifest-schema 400, and the missing-POS-org 409. Existing-tenant mode returned those precise statuses unchanged (pinned in `tenant-scoped-uniqueness.test.js`), so the same manifest answered 400 to a tenant admin and 500 to the super-admin provisioning that tenant — the operator-visible status code, the `errors` array and the "nothing was written at all" guarantee all regressed, and the quoted reason gained a doubled period (`…remove categoryName.. All partial data…`) because every pre-flight message already ends in `.`. Data integrity was never at risk (the undo replay is clean; M5 and the rollback suite prove zero surviving rows), so the fix belonged on the STATUS/envelope layer. **Now fixed**: deliberate rejections are stamped with a module-private `Symbol` on the Response and the saga hands them back after the undo; the meal-category pre-flight additionally runs BEFORE the shell, so that rejection writes nothing at all. The duplicate-SKU / duplicate-POS-user 409s deliberately stay `500 …rolled back.` — they are BATCH failures, committed state was undone, and `tenant-import-identity.test.js` M5 pins that contract.
- **Classify an error by INTENT, never by how much state its aftermath left (2026-10-02, A2)**: an undo/saga log's length answers "what must I undo", never "was this rejection deliberate" — the two coincide only while the log is empty, and in a two-phase writer (provision a shell, then import into it) the log is populated before the first real validation runs. Stamp the distinction on the RESPONSE instead: a module-private `Symbol` property (`DELIBERATE_REJECTION`) set on the rejection the handler authored, read by the wrapper. Why that carrier and not another: a header leaks the classification to clients, a wrapper class needs the throw-path reconciled with it, and — decisively — a raw D1/R2 error is a THROW, never a Response, so a thrown failure can never masquerade as an authored 4xx. Keep the two exits visibly distinct at the call sites (`reject(400, …)` vs `fail(409, …)`), and expect a `status >= 400 && status < 500` heuristic to be wrong the moment a section starts answering an honest 409 for a mid-write batch failure. Two corollaries from the same commit: (a) **rolling back must not mangle the message** — every pre-flight message ends in `.` and the rolled-back template appends `. `, so quoting a reason into it doubles the period; return the original Response instead of rebuilding one; (b) **a pre-flight can only be hoisted above provisioning if its answer cannot depend on rows provisioning is about to create.** `menu.meals[].categoryName` qualifies (a tenant id not yet INSERTed owns no `meal_categories`, and the shell creates none — the answer is identical on both sides of the shell); `campId` does NOT, because the shell creates the very `projects` row its references resolve against. Hoisting the second one would have turned every `campId` in a create-mode manifest into a guaranteed 400.
- **`ensureTenantOrg` can leave an UNTRACKED `pos_organizations` row behind a saga rollback (2026-10-02, A2 — known, benign, NOT fixed)**: the identity route tracks org/store/mapping only `if (organizationId && priorMapping.length === 0)`, i.e. only when `ensureTenantOrg` handed an id back. `ensureTenantOrg` swallows every error and returns `null`, so the window between its `INSERT OR IGNORE INTO pos_organizations` and its `SELECT id … WHERE slug = ?` is a hole: if that SELECT fails, the org row is committed, no id comes back, nothing is logged, and the rollback deletes tenants/admins/project while the org row survives (measured while writing S1 — `expectBaseline()` caught it). It self-heals: a retry's `INSERT OR IGNORE` is ignored, its slug SELECT finds the row and reuses it, so the next import provisions normally. Left alone deliberately — closing it means tracking a row the saga cannot identify uniquely (the org is found by slug, not by the tenant), which is a bigger change than this fix's remit. Anyone writing a strict "zero rows survive" assertion on an injected `ensureTenantOrg` failure should inject on the org INSERT (nothing written), not on the slug SELECT (orphan row).
- **Snapshot a row-count baseline AFTER seeding fixtures, not before (2026-10-02, A1)**: a `beforeEach` baseline captured before a fixture is inserted inside the test body makes `expectBaseline()` fail on the fixture's OWN rows ("tenants rows: expected 1 to be 0") and reads as a handler defect. - **A NULL tenant is not the same as a FAILED tenant lookup — never render one as the other (2026-10-03)**: a D1 outage answered every tenant host (`acaciacamp.com`, `michaelshouse.sinaicamps.com`) with the Worker's 500 (`backend/src/index.js` `app.onError` → `errorResponse('Internal Server Error', 500)`), `middleware/tenant.ts` swallowed it in its `catch`/`if (res.ok)` and every page read `!tenant` as "this property does not exist" → the branded **404**. A 404 is a claim about existence, so the outage lied three ways at once: to a crawler (indexed as gone), to the monitor (`status.sinaicamps.com` saw a healthy 404 while every tenant was dark) and to a human booking a stay. The distinction is now modelled ONCE as `lib/tenantLookup.ts`'s `TenantLookupState` (`skipped | ok | not-found | failed`), classified from the RESPONSE (`classifyTenantLookup`): **only a 404/410 — or a 2xx body with no `id` — is `not-found`; a 5xx, 429, 401/403, a status-less response, a throw, the 5s abort, or a body that is not JSON is `failed`.** It rides on `Astro.locals.tenantLookupState` (published by the middleware in BOTH resolution paths: `getTenantSSRData().lookupState` and the `locals` write), and `ZoneGuard.astro` is the single render site (`resolveTenantGuardState` → 404 `NotFoundPage` vs 503 `TenantOutagePage` + `Retry-After: 60`). Three rules follow from it: (1) **default the state to `skipped`, never to `not-found`** — a request that never ran the lookup (marketplace host, `/admin|/pos|/auth` early return) must not be readable as a positive "no such tenant"; (2) **zone exclusivity outranks the outage** — `resolveTenantGuardState` checks `routeForbidden` FIRST, so a failed lookup can never turn `/camps` on a tenant host into a 503 and loosen `routeZones.ts`; (3) **classify from the response, never from the emptiness of a downstream variable** — a per-page `!tenant ? 404 : …` is the exact shape that hid the outage, and six pages (`book`, `menu`, `rooms`, `camp/[id]/{book,menu}`, `storefront/index`) plus `TenantLanding` all had one. Known boundary, deliberate: the middleware lookup is keyed by HOST, so marketplace deep links (`/camp/{id}/book`) still answer 404 for an id the API could not answer during an outage — covering them would need a per-page classification (or an extra API call on the healthy path), which is the per-page duplication this fix exists to remove.

- **An audit's summary table can fail to reconcile with its own entry list, and the fix is to publish both numbers rather than to pick one (2026-10-06, docs-p8c)**: audit A's class table sums to **94** while its own by-doc breakdown and its entry headings both come to **83**; audit B has **135** headings against a reported **134** (the extra is `T‑0`, a provenance table carrying no class). Neither audit counted the gap markers **nested inside a `MATCHED` entry** — counting them yields **13 `UNVERIFIED` items** and **10 `UNDOCUMENTED` items** against reported 11 / 7 and 4 / 3. `docs/99-gaps/code-vs-docs.md` therefore prints the sources' figures unchanged *and* a recount, with the three discrepancies itemised. **Never "correct" a source audit's totals while consolidating it**: the source stays the record of what that audit claimed, the consolidation is the record of what actually reconciles. A summary table that does not add up to its own body is the same defect class the audit exists to find — and it is invisible unless you recount.
- **Entry IDs collide across audits, so a consolidation keyed on the ID alone silently drops entries (2026-10-06, docs-p8c)**: both gap audits number entries by folder initial — audit A used `S‑1…S‑11` (API_SURFACE_MAP) and `R‑1` (01-architecture/README); audit B used `S‑1…S‑19` (security-guide) and `R‑1…R‑19` (09-plans). **12 of the 218 entries share an ID across the two sources.** Keying the placement lists on the bare ID made 12 entries match the wrong bucket, and the arithmetic (`80 + 15 + 10 + 112 = 217`, not 218) is what exposed it. Fix: key on `(audit, id)`, emit the ID with its original typography (the audits use U+2011 `‑`, not ASCII `-`), and **assert that the placement lists plus the controls list sum to the extraction count** before writing anything. The same rule generalises: in any vault where notes are cross-referenced by a short ID, the ID is only unique *within a document*.
- **The migration-head drift has THREE carriers and the one outside the vault is the one every agent reads first (2026-10-06, docs-p8c)**: both audits scoped `docs/` and both found the drift inside it — `docs/07-data/migrations.md:29` (37 files / head `0123`) and `docs/98-history/sessions/WAVE6_EXIT_REPORT.md:23` (99 migrations / `0099`) — while **repo-root `AGENTS.md:70` says "D1 schema migrations (53 files — Layer 3)"**, a file that is not a vault doc at all and that every agent opens before anything else. Truth: `ls backend/migrations/*.sql | wc -l` → **40**, head `0127_meals_tenant_composite_pk.sql`, sequence `0001–0014` then `0100–0127` with `0109` and `0125` deliberately absent; `legacy/` holds the **99** that both stale figures are really counting. Two docs already publish the correct figure (`docs/01-architecture/ARCHITECTURE.md` §5 and the `07-data/README.md` drift callout), which is why this is three stale files and not a folder-wide ignorance. **An audit scoped to a documentation folder structurally cannot find drift in the repo-root agent instructions — put `AGENTS.md` and the root `README.md` in scope explicitly**, and remember that a *third* distinction rides along: `0127`'s own header is `⚠️ PENDING-APPLY … committed but NOT applied`, so "head" means *highest in the tree*, not *applied in the ledger*, and no doc says which one it means.
- **A `## Gaps` placeholder becomes a real pointer, and then the contributing rule that justified it is history — do not leave the contradiction undocumented (2026-10-06, docs-p8c)**: all eleven folder MOCs now carry a live pointer into `docs/99-gaps/` with that folder's own entry counts (`01-architecture` 9/2/2, `02-api` 10/0/3, `03-frontend` 10/6/0, `04-testing` 9/1/0, `05-operations` 8/3/0, `06-security` 4/1/1, `07-data` 5/0/1, `08-guides` 5/2/1, `09-plans` 13/0/1, `10-tenant-import` 7/0/1 — gap / unverified / undocumented). `docs/contributing.md` still says the placeholder "stays byte-exact until the gaps sweep runs", and the three files in `docs/_templates/` still carry it. **The templates are correct and should keep it** (a template is a doc that has not been audited yet); `contributing.md` is now historical. Because this pass is audit-only and fixing a doc is out of scope, the supersession is recorded inside `docs/99-gaps/README.md` rather than by editing `contributing.md` — **when a rule is superseded but out of scope, write the supersession into a file you own and name the file it contradicts**, so the contradiction is visible to the next agent instead of silently resolved.
- **The `docs/` vault audit must still read repo-root `AGENTS.md`, and `98-history` needs its own rule because a dated record is not a claim about the present (2026-10-06, docs-p8c)**: neither audit touched `98-history`, deliberately — the bucket's invariant is that a dated claim is checked against the tree **as of its `created:` date**, so `WAVE6_EXIT_REPORT.md`'s "99 migrations" was **true on 2026-09-21** and the recorded action is *annotate* (mark 99 as the pre-squash count now in `legacy/`), never *correct*. The same rule retires `test-count` entries: `ARCHITECTURE.md`'s 124/2701 rows are dated to their commits and are drift, while a labelled snapshot (`PERF_BASELINE.md`'s historical tables, action `DEFER`) is not a defect and must not be "fixed". Still out of scope in both audits and named as such in `docs/99-gaps/README.md`: `docs/README.md`, `docs/contributing.md`, and the path-preserving stubs `docs/API_SURFACE.md` / `docs/tenant-import.md`. **`docs/README.md` — the vault MOC — still has no link to `docs/99-gaps/`,** so the only ways in are the eleven folder MOCs; that is a one-line addition for the next vault-MOC pass and was left out here because this spec's output list is the four notes plus the `## Gaps` pointers.
- **A wikilink resolver that tries the PATH branch before the basename branch will silently swallow the one ambiguous stem in the vault (2026-10-06, docs-p9)**: `docs/README.md`'s vault-relative stem **is** `README`, so an `if target in vault_relative_paths: return it` check resolves every `[[README]]` to the root index and reports the vault **clean** — while `README` names **22 files**, one per folder, and `docs/contributing.md:49` says so in as many words ("copies), so `[[README]]` is ambiguous and `[[98-history/merged/README]]` is not"). Same corpus, opposite verdicts, and the p6 gotcha above ("count distinct RESOLVED PATHS") does not catch it because the resolver *did* return one path — a wrong one, confidently. **Rule: a bare stem may never resolve through the path branch; only a target containing `/` may.** A bare stem must resolve against the full stem index, and >1 candidate is *ambiguous* — a third class, reported separately, neither broken nor fine. That one precedence rule moved the p9 numbers from `0 ambiguous / 3 broken` to **18 ambiguous / 3 broken** on identical inputs, and 17 of the 18 were about to be written off as resolved. **Generalises: whenever a file sits at the root of the resolution space, its bare name shadows every duplicate of itself — put the path check behind a `"/" in target` guard, or add a fixture whose target is that file's own stem.**
- **"Orphan" is not a property of a note, it is a property of a DEFINITION — and the vault's own index files are the notes a strict orphan rule always condemns (2026-10-06, docs-p9)**: auditing all **97** notes for "linked from nowhere but the index" returns **6**, and **5 of the 6 are not defects**. `docs/README.md` is linked from **11** folder MOCs and is flagged only because every one of those MOCs is *itself* named `README.md`; the four `98-history` notes (`AUDIT_TS_DEPS_FINDINGS`, `IMPLEMENTATION_PLAN`, `POLISH_PLAN`, `audit-2026-09-30-monitor-404`) are each linked from **their own bucket MOC plus the `98-history` MOC**, which is precisely the curation a MOC exists to provide. Under the looser "no inbound link at all" reading the answer is **0**. The one real orphan is `docs/contributing.md` — the vault's frontmatter/MOC/link contract, reachable from exactly one place (`99-gaps/README.md`'s `## Related`), and the string `contributing` appears **nowhere** in the root MOC, so the entry point cannot route a contributor to the rules. **Rule: when an orphan sweep returns a cluster dominated by MOCs, the definition is the finding, not the notes** — report orphans in tiers (zero inbound / index-only / label-rescued), say which tier each note is in, and fix only the notes that are unreachable by *any* path. A note linked from its own folder index needs no second link, and adding one is duplicate navigation dressed as a repair.
- **A "missing frontmatter" count of 0 is only believable if the checker was proved able to fail (2026-10-06, docs-p9)**: the check (`title` + `tags` + `updated` present and non-empty) reports **97/97 valid** across the vault, and a minimal YAML parser that mis-handles an empty block list returns `[]` for every field — which reads as *missing everything* rather than as a crash, or, inverted, a parser that swallows keys returns "valid" for every file. Three synthetic fixtures settle it in one run: `tags: []` → flagged, no frontmatter block → flagged as `<no frontmatter block>`, valid note → clean. **Same rule as the resolver guards: every "no defects found" number needs a fixture that proves the detector fires.** A green audit and a broken auditor are indistinguishable from the output alone.
